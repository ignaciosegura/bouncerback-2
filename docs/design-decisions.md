# Bouncerback — Design Decisions

Decisions taken with the user while planning, with their reasons, moved here from `docs/implementation-plan.md`. They have also been written into the relevant docs; if this file and another doc disagree, the other doc is the source of truth and this file should be corrected. Read the section for the area being changed.

---

### Tooling & architecture
- **Bundler:** Vite (fast ESM dev server, pairs well with PixiJS v8's async `app.init()` and with Capacitor).
- **Language:** plain JavaScript/JSX — matches `eslint.config.js` (no TS parser) and `project-structure.md` (all `.jsx`/`.js` files).
- **PixiJS v8**, matching the async `app.init()` pattern in `docs/react-pixi-example.jsx`.
- **No routing library** — `App.jsx` is a simple state-based screen switcher, per `project-structure.md` ("router / screen switcher").
- **Screens only:** every screen lives in `src/screens/` and is built from the generic components in `src/components/` (`Button`, `Menu`, `TextBox`, `Overlay`, `HUD`, `Screen`). There are no separate `components/*Menu.jsx` files.
- **Game Over and You Win! are full screens**, not overlays: they replace the Game Screen (`GameOverScreen.jsx`, `YouWinScreen.jsx`). Only the Pause screen (cycle 2) is an overlay.
- **Assets are imported through Vite.** `assets/` stays at the repo root; code imports files (`import.meta.glob` / `?url`) so built filenames get a content hash (cache-busting) and only used files are shipped. The font is referenced from `src/index.css` by relative path so Vite processes it too.
- **Persistence:** `localStorage` for settings (music/SFX volume) and high score. Works identically in browser and Capacitor WebView; no extra plugin needed.
- **Orientation lock:** CSS/layout-based landscape in cycle 1; the `@capacitor/screen-orientation` native hard lock in cycle 2. A "rotate your device" overlay was planned (Phase 11) and dropped as won't do: the native apps are locked to landscape, and the web build isn't a supported play target. The plugin isn't in `docs/tech-stack.md`'s stack table but is needed to satisfy AGENTS.md's "forced landscape orientation" on native.
- **Tests:** no test framework is specified in the docs. A few Vitest unit tests for pure logic (score formulas, level-loader math) are an optional nice-to-have; PixiJS/DOM rendering isn't practically unit-testable.
- **Mobile app icon:** `assets/images/icon.png` is the real square app icon; native icons/splash are generated from it in Phase 10.

### Gameplay
- **Bounce:** a paddle reverses an atom's direction exactly — it travels straight back through the core and out toward the opposite side of the ring (this is what makes the tap-at-the-core capture possible).
- **Late bounce (grace window):** an atom reaching the paddles (`contactDistance`) with no paddle covering it doesn't escape yet: it keeps moving and is checked every frame until its center crosses the ring (`RING_RADIUS`), and only then escapes (life lost). A paddle set inside that window bounces it, mirrored around `contactDistance` so it stays on the beat — a visible jump back of up to twice the window, accepted as a trade-off.
- **Paddle lifetime** (`paddles.duration`) starts when the paddle is set (pointer released). While dragging, the paddle is inactive and doesn't expire.
- **Paddle lifetime fade (cycle 2):** a set paddle stays at full opacity for the first half of its lifetime; during the second half its opacity drops linearly from 100% to 20%, then it disappears. A freshly set paddle is always fully visible, and the fade starting means half of its time is gone. The 20% floor keeps a paddle that is still blocking atoms clearly visible until the moment it expires. Dragged (inactive) paddles are always drawn at full opacity; the fade is purely visual and doesn't change the collision rules.
- **Paddle bounce flash (cycle 2):** a subtle echo of the paddle that bounced the atom: a semi-transparent white arc with the paddle's angle, arc length and thickness, starting on top of the paddle and drifting outward by about half a paddle thickness while fading out in 0.2 s, like a slight recoil. It never reaches further inside the ring than the paddle itself, so it never clutters the playable area. Each paddle has a single echo: a new bounce on the same paddle while its echo is still playing interrupts it and restarts it from the beginning. Two different paddles can show their echoes at the same time. The echo plays to the end even if its paddle expires or is replaced right after the bounce. Purely cosmetic: eye candy that complements the `bounce` SFX.
- **Paddle replacement warning (cycle 3):** with two paddles set, placing a third one (first in, first out) used to remove the oldest paddle with no warning at the moment of release. Now, while paddles are being dragged (mouse, touch or a controller stick), every set paddle that their release will push out turns red (`#FF0000`): the oldest `active + dragged − MAX_ACTIVE_PADDLES` set paddles, oldest first. With two paddles set and one being dragged, that's the oldest one; with both sticks dragging, both. It's computed every frame from the current paddles, so it's always right: a paddle that expires during the drag simply expires (all paddles have the same lifetime, so the oldest expires first, and the warned one is always the one that would go). The switch is **instant**, overriding the 0.5 s default for color changes: a drag can be released in a fraction of a second, and a fading cue would barely show. The red paddle keeps its lifetime fade (opacity) and stays red until it's removed. Its bounce echo stays white. The paddle being dragged keeps its white outline. Red reads as "about to go" in the game's feedback colors (charged atoms already head to red as they become dangerous to keep); the one-life-left background darkens from `#660000` to `#550000` so the red paddle stands out on it too. The screen transitions' transition dark red (`#660000`) is a separate color and doesn't change (graphical-specs "Colors").
- **Larger core (cycle 2):** the core radius grows 25%, `CORE_RADIUS` 20 → 25. The capture window (`CORE_CROSSING_DISTANCE = CORE_RADIUS + ATOM_RADIUS`, "the atom overlaps the core") grows with it, 40 → 45 px from the center, so capturing gets slightly easier. That's intended: the window the player sees and the window in which a tap captures stay the same. `CAPTURE_TAP_RADIUS` (60) is still larger than the window and doesn't change.
- **Capture window pulse (cycle 2):** a charged atom (charge ≥ 3, `MOVING`) that overlaps the core emits one pulse per beat of the music. Beats are counted on the level's beat grid (`floor(time / secondsPerBeat)`, where `time` starts together with the music), not from the moment the atom enters the core, so the pulses match the music. Atoms spawn at random moments, so the entry point is off-grid. The first pulse comes on the first beat after entry, not on entry. At most 3 pulses per crossing (`MAX_PULSES_PER_CROSSING`): on long crossings (`travelTime` 16) later beats come as the atom is leaving the core, so most of their fade would play once it can no longer be captured. With the larger core a crossing lasts 90 × `travelTime` / 305 beats (≈ 2.4 beats at `travelTime` 8, the shortest in the current levels), so every crossing gets at least two pulses. A pulse is a filled circle in the atom's current color, drawn behind the atom and following it. Its radius grows from `ATOM_RADIUS` to `2 × ATOM_RADIUS` (ease-out) while its alpha goes from 0.5 to 0 over one beat, so each pulse ends as the next one starts. The capture test and the pulse test share one predicate, so the cue can never disagree with what a tap does. Purely visual; no SFX.
- **Capture animation (cycle 2):** a captured atom no longer vanishes instantly. Over **0.5 s** it moves from where it was tapped to the center of the core while shrinking from full size to 0, both on the same ease-in (quadratic) curve: slow at first, fast at the end, so it looks sucked into the core. It stops travelling along its path the moment it's captured. The score and the `capture` SFX still happen on the tap; the animation is purely visual. A capturing atom keeps its current color, can't be captured again (a second tap takes the next capturable atom, if any), doesn't pulse, and ignores collisions (it's already inside the core). A pulse in progress is cut off at capture, since the atom is no longer capturable. If the core collapse starts during the animation, the animation finishes as normal (like an escaping atom's fade) and the atom doesn't count for containment, because it was already captured.
- **`paddles` is required** in the level schema. Suggested starting values: `angle` 30°, `duration` 3 s.
- **Paddle count (`paddles.count`):** how many paddles can be set at the same time is a per-level value, not a fixed two: fast, dense levels can allow more (four, say) so the player can cover more of the ring. Setting one more than the count removes the oldest (first in, first out), as before. It's optional and defaults to 2, so existing levels play exactly as they did. At least 1 (checked by the level loader, like the other ranges the schema doesn't express). The replacement warning and the controller sticks follow the level's count instead of `MAX_ACTIVE_PADDLES`.
- **Start delay:** entering a level shows the ring and core, then waits **3 seconds** before the timer, the atom emitter, the level track and player input start. The menu track fades out during the delay and the level track is preloaded, so music and timer start together.
- **Level start animation (cycle 2):** the ring and core aren't drawn straight away at full size; they grow in, one after the other. **0 → 0.25 s:** the ring's radius goes from 0 to `RING_RADIUS` (ease-out, quadratic); the core isn't visible yet. **0.25 → 0.75 s:** the core's radius goes from 0 to `CORE_RADIUS` (ease-out, quadratic). Both keep their 2 px outline while growing (redrawn, not scaled). It plays inside the 3-second start delay, from the moment it begins, so the delay stays 3 s and there are still 2.25 s of stillness before play starts. It replays on every level start, Try Again included. Purely visual: no SFX, and nothing else happens during the start delay that it could clash with (no atoms, paddles or input).
- **Core collapse (timer reaches 0):** spawning stops, paddles disappear, input is disabled and every atom inside the ring is pulled into the core over **3 seconds** (**2 seconds** from cycle 2, see "Core collapse animation"). Nothing can escape, so no lives can be lost; atoms already fading out after escaping are ignored. Then the You Win! screen is shown.
- **Core collapse animation (cycle 2):** replaces cycle 1's spiral pull and plays together with the `vortex_creation` SFX. It has two stages:
  - **Settle (0 → 1.85 s):** the core's radius grows from `CORE_RADIUS` to `RING_RADIUS` (ease-in-out) while its fill fades from transparent to `#888888` (fill alpha 0 → 1 with the same easing, so it looks right over the dark red one-life background too). The outline grows with it and turns from white to `#888888` with the same easing. At the same time every collapsing atom slows down to a stop with an ease-out (quadratic) curve. It keeps moving in its own direction and starts at its playing speed, so there's no jolt at the start. That gives it a total drift of `speed × 1.85 / 2`, half the distance it would cover at full speed.
  - **Collapse (1.85 → 2 s):** the core shrinks from `RING_RADIUS` to 0 (ease-in). Every atom moves from its resting point to the center and shrinks from full size to 0, using the same ease-in curve, so the atoms and the core arrive together.
  - No collision checks during the core collapse. An atom that was near the ring (or already in the grace window) can drift past the ring before it stops. That's accepted: it still collapses into the core and never escapes. Atoms keep their charge colors and are drawn over the grey core; nothing spins.
- **Last life zoom (cycle 3):** losing the last life used to just freeze the playfield for 1 s before Game Over, with little impact. Now, after a moment, the camera zooms in on the atom that took the last life. It plays in three beats: **freeze (0 → 0.5 s):** every other atom stops at once, while the last atom keeps escaping at its normal speed and direction, at full opacity (no fade), then stops too; **zoom (0.5 → 1 s):** the view zooms in **8×** (ease-out) on the point midway between where the atom crossed the ring and where it stopped, moving that point to the center of the screen; **hold (1 → 2 s):** the zoomed view stays, with the atom fully visible, until the Game Over screen-out starts 2 s after the loss (was 1 s). The player first sees everything stop, then the zoom shows which atom escaped. **Choices made with the user:** all of the above. *(The first version of Phase 36 started a 10× zoom on the crossing point at once, with the atom escaping and fading at 1/3 speed. In play it felt too sudden.)*
  - **Focus:** midway between the exact point where the atom's center crossed the ring (`RING_RADIUS` along its position angle) and the atom's frozen center, so both the crossing and the atom are in view. After 0.5 s at full speed the atom is up to about 57 px past the ring on the fastest level (about 460 px at 8×), so centering on either one alone could leave the other partly off screen.
  - **Zoom:** the whole playfield (ring, atoms, paddle echoes) scales by up to **8×**. It's a camera move, so line widths scale too: the ring's 2 px outline is 16 px at the end. With `e = easeOutQuad(t / 0.5)` the scale is `8^e` (even zoom speed to the eye, which a linear 1 → 8 isn't) and the focus point's offset from the screen center is its normal offset × `(1 − e)`: it glides straight to the center while the playfield grows around it. *(Moving the camera's center straight from the core to the focus point instead would push the focus off screen mid-zoom.)*
  - **Freeze:** every other atom stops at once, including atoms that were already fading out after escaping or being captured (they used to finish their animations during the Game Over delay). Paddles disappear as today. Paddle bounce echoes finish normally (0.2 s, cosmetic). The last atom never fades: it must be clearly visible when the zoom lands.
  - **Round shapes at 8×:** PixiJS builds circles and arcs as polygons sized for their drawn radius, not their on-screen size: the atoms get 15 sides and the ring 60, which would show as flat sides and corners at 8×. The atoms and the ring are drawn as polygons with enough points to stay round at 8×. Both are drawn rarely (atoms once, the ring during the start animation), so the extra points cost nothing per frame.
  - The `destroy` SFX, the Game Over screen and the HUD don't change. No state goes to React.
- **Score** (`level` = the level's number, 1–5):
  - Bounce: `10 × level × charge`, using the charge the atom has as it hits (before the bounce adds one).
  - Capture (tap-destroy at the core): `100 × level × charge`.
  - Containment at level end: `200 × level × charge` for every atom taken by the core collapse, plus `500 × level × remaining lives`.
  - Time bonus at level end: `initial timer value (tenths of a second) × level`. Example: a 2-minute level 3 gives `1200 × 3 = 3600`.
- **Additional mechanics (cycle 3):** bouncing atoms back with paddles is the only core mechanic; the rest are additional, chosen per level in `additionalGameMechanics`. `atom capture` is the charge-and-capture mechanic below; without it atoms stay at charge 1 and can't be captured. A level's mechanics never change while it is played. Part of the "Additional game mechanics" task; see Phase 48.
- **Charged atom hold (cycle 3):** the press holds a capturable atom and the release captures it (Phase 49). Decisions made with the user: a held atom scores at a rate per second, flat (not scaled by level or charge), paid in steps so the HUD doesn't update on every frame; both are tunable and live only in `src/game/chargedAtomHoldSettings.js`. The unpaid remainder is paid when the hold ends. Only one atom can be held at a time, by the input that held it; other presses meanwhile hold nothing. On controller buttons only a press that held an atom can capture. Pausing cancels the hold and the held atom is captured on resume. The core collapse takes a held atom as any other. The initial values were 60 points per second and a step of 1 (every point), which makes the HUD update up to 60 times per second: the one exception to "no high-frequency state in React" (AGENTS.md rule 2), accepted because it's one small number; raising the step lowers it.
- **Charge:** atoms start at 1, gain +1 per bounce, capped at 10; they can be tap-destroyed at the core once charge ≥ 3.
- **High score:** common to all levels, updated and saved the moment it's beaten, visible on the HUD, Game Over and You Win! screens.
- **Timing math:** `secondsPerBeat = 60 / bpm`. Atom pixel speed = `contactDistance / (atoms.travelTime × secondsPerBeat)`, where `contactDistance` is the distance from the core at which an atom touches a paddle (ring radius − half the paddle thickness − atom radius), so atoms reach the ring exactly `travelTime` beats after leaving the core. Initial timer (tenths of a second) = `round(duration × signature × secondsPerBeat × 10)`. Spawn interval = `atoms.barsInterval × signature × secondsPerBeat`: an atom can only appear once every `barsInterval` bars, at a random moment inside each interval.

### Layout & UI
- **Playfield scaling:** ring radius ≈ 31% of viewport height (a ring about 62% of the screen height, as in the GAMEPLAY mockup), centered; the core, atoms and paddle thickness scale with it. Recalculated on window resize/rotation. Because atom speed is defined in beats, gameplay timing is the same on every screen size.
- **Font sizes** (per `graphical-specs.md`): 24px HUD, 32px menu buttons, 64px "GAME OVER" / "YOU WIN!" titles. Line height 1, weight normal, always uppercase (except the informative texts: the Intro note, the Main Menu credits, the How To Play instructions and the Gameplay tips, which are mixed case: see "Mixed-case text" below), single line.
- **UI scaling:** the mockups are 1:1 at 1920x1080. All UI sizes are written in mockup pixels (`--u` in `src/index.css`) and scale with the viewport (min of height/1080 and width/1920, floor 0.4px), so every screen keeps the mockup proportions on phones too. Button padding is 0.5em, as in the mockups.
- **Mockups win on on-screen text:** where a doc and a mockup disagree, follow the mockup. Labels: "HI-SCORE" (not "High Score"/"Best Score"), "TRY AGAIN" (not "Play Again"), "<<< BACK".
- **Level Select** buttons show each level file's `name` (LEARN, FEMTOCOSMOS, CHRONOSAEDR0N, MEKANOMANCER, NEUTRONIKA). All levels are unlocked in cycle 1; unlocking comes in cycle 2 (Phase 13: levels grouped in tiers, one row per tier, locked levels shown as dashes).
- **Try Again** restarts the same level from scratch (score reset to 0, lives from the level file).
- **Menu background animation (cycle 2):** `assets/motion/intro_animation.json` (Lottie, 1920x1080, 60 fps, transparent background, light-grey/white lines) plays behind the Intro, Main Menu, Level Select and Settings screens (only Main Menu, Level Select and Settings from Phase 26), on top of the `#D8D8D8` background. It plays uninterrupted while the player moves between those screens: it is one instance mounted in `App.jsx` outside the screens, so switching screens never restarts it. Leaving for the Game Screen unmounts it; returning to the menus from Game Over / You Win! starts it again from frame 0. The file's timeline is 10,800 frames (180 s), but its content ends at frame 7485 and the original project is lost, so it can't be re-exported: we loop frames **0 → 7785** (the content plus 5 s / 300 frames of the empty tail) and skip the rest of the empty tail. The file uses `loopOut('cycle')` expressions on two time-remapped layers, so it needs lottie-web's SVG player with expression support (`lottie_svg`), not `lottie_light`. It scales like a cover background (`xMidYMid slice`): it fills the whole viewport, cropping top/bottom on screens wider than 16:9, and ignores safe areas.
- **Enter screen & menu music start (cycle 2):** the animation and `main_title.mp3` were made together, so they must start at the same moment (roughly: no frame-by-frame sync, and no correction if they drift apart later; the track is 164 s and doesn't repeat, the animation loops every 129.75 s). Browsers block sound until the player interacts, so the app now opens on an **Enter screen** with a single `ENTER BOUNCERBACK` button. Pressing it unlocks audio (`silence.mp3`, moved here from the Intro tap) and goes to the Intro, where the menu track starts **at full volume, with no fade-in**. The animation doesn't start on mount: it waits on frame 0 until the menu track actually starts playing (Howler's `play` event, not the tap), so a slow load never puts them out of step. The Enter screen preloads the track so it's usually ready by the time the button is pressed. The Enter screen uses the light layout with no animation, so the switch to the Intro is seamless; it appears on every launch, on the web and in the native apps. The Intro tap now only goes to the Main Menu. Coming back to the menus from Game Over / You Win! keeps the usual 0.5 s fade-in, and the animation again starts when the track does. *(Phase 26 replaces this screen flow: see "Intro & Main Menu merge".)*
- **Intro & Main Menu merge (cycle 2):** with the Enter screen in place, the logo-only Intro became an extra tap with nothing to do. The updated mockups replace it: the `ENTER BOUNCERBACK` screen **is** the Intro now (`INTRO.png`), and the logo moves to the top of the Main Menu (`MAIN MENU.png`). The flow is **Intro (`ENTER BOUNCERBACK`) → Main Menu**. The Intro is still silent, opaque and without the animation. Pressing the button unlocks audio and goes straight to the Main Menu, where the menu track starts at full volume with no fade-in and the animation starts with it. The track is started from the button's click handler, not from the screen-change effect. The effect can't tell a first arrival from a return from Game Over / You Win!, and those returns must keep the 0.5 s fade-in. `playTrack` ignores a request for the track already playing, so the Main Menu's own `playTrack(MENU_TRACK)` then does nothing. The menu background animation now covers three screens: Main Menu, Level Select and Settings. The logo is always shown on the Main Menu, including when coming back from Level Select, Settings or a finished level. Its layout (graphical-specs "Game logo") is 1518 px wide with its top 182 px from the top of the screen, and 229 px from the logo to PLAY. The buttons move down from their centered position to make room for it.

- **Screen transitions (cycle 2):** every screen change is the same two-part transition, inspired by old TV sets (graphical-specs "Screen transitions"): a 1 s **screen out** (fade out; color blending gradually to transition dark yellow `#666600` over 0.5–0.75 s, then to transition dark red `#660000` over 0.75–1 s; a slight vertical vibration at 0.875–1 s), then a 0.5 s **screen in** (fade in, nothing else). The first screen on launch (Intro) plays the screen-in only. **Only the screen's elements animate** (the direct children of `.screen`: menus, text, the logo, the result scores, the HUD), **not the screens**: the screen background, the menu background animation and the game canvas (its drawings included) stay still, and the background changes at once at the swap. All the animation is CSS (`@keyframes` in `src/index.css`). React only switches a class on a wrapper around the background and the screen: it keeps the old screen up during the screen-out, swaps on its `animationend`, and clears the class when the screen-in ends; CSS alone can't keep an unmounted screen on screen. No timers, and no animation state in React. The tint recolors the elements: it animates the screen's foreground color `--fg` (registered with `@property` as a `<color>`, so it blends), which the text, borders, pressed buttons and HUD lives already use, so black elements on the light menus and white ones on the dark screens both reach exactly `#666600` / `#660000`. The Main Menu logo is an `<img>` today and can't follow `--fg`, so it becomes a CSS mask filled with the foreground color. *(Later replaced by an inline SVG filled with `currentColor` (`src/components/Logo.jsx`; see graphical-specs "Game logo"), which follows `--fg` the same way.)* Taps are ignored while a transition runs. The music follows the screen that is actually shown: it changes when the new screen appears, so the menu track (and with it the menu animation, which mounts with the Main Menu) starts together with the Main Menu, and the level music keeps playing while the Game Screen's HUD fades out after Game Over / You Win!. The Intro button therefore only unlocks audio. The menu track's first start (no fade-in) moves back to the screen-change effect, which now tells a first arrival from the Intro apart from a return from a finished level (this replaces the click-handler start from "Intro & Main Menu merge").

- **Logo blink (cycle 2):** the pieces of the Main Menu logo blink at random. A piece is one element of the inline SVG (`src/components/Logo.jsx`): each letter, with the E's three bars counted separately, 13 in total. The O's ring and dot are one path, so they blink together. About once every 2 seconds one piece blinks. The wait before each blink is random, uniform between 0.5 and 3.5 s (2 s on average). A uniform range is used instead of fully random (Poisson) timing, which would give long gaps and bursts. The piece is picked at random, never the same one twice in a row. A blink turns the piece white (`#FFFFFF`, `--color-white`) at once, then fades it back to the logo's color over 0.15 s, linear. The wait is always longer than the blink, so at most one piece blinks at a time. The first blink comes after the first random wait. It runs whenever the Main Menu is on screen, screen transitions included: the fade ends on the current foreground color, so during the screen-out a blinking piece fades to the tint color like the rest of the logo. The animation is CSS. The random timing is a `setTimeout` chain in `Logo.jsx` that only toggles a class, with no React state.

- **Intro headphones note (cycle 2):** the Intro shows "GRAB YOUR BEST HEADPHONES FIRST ;)" *(mixed case since Phase 29: "Grab your best headphones first ;)", see "Mixed-case text")* on one line above the `ENTER BOUNCERBACK` button (graphical-specs "Intro screen note", `INTRO.png`). It uses the menu size (32 px), the same as the button's text. It has no border, so it isn't mistaken for a second button; the Game Over / You Win! titles and scores already set this precedent for text that isn't interactive. The button stays centered on the screen, and the note's line box ends 59 px above it, measured on `INTRO.png` (text line at 415–447 px, button border from 506 px). It's a direct child of the screen, so the screen transitions fade and tint it with the button without any change to the transition code.

- **Main Menu credits (cycle 2):** the Main Menu shows two credit lines at the bottom (graphical-specs "Main Menu credits", `MAIN MENU.png`): "A game by NIK NAK STUDIO" and "Music and sfx by MAN FROM SPACE", in mixed case as the mockup writes them (see "Mixed-case text"). They use the HUD size (24 px), have no border, and each line is centered on its own. Only the names are links: NIK NAK STUDIO → `https://niknak.es`, MAN FROM SPACE → `https://manfromspace.com`, both opening in a new tab. The links look exactly like the text around them: same color, no underline, and no feedback on hover, press or focus. The block is pinned to the bottom of the screen (absolute position) instead of joining the centered logo + buttons group, so the logo and buttons keep their current layout. It's a direct child of the screen, so the screen transitions fade, tint and shake it with the rest.

- **Mixed-case text (cycle 2):** all text is uppercase (forced by `text-transform: uppercase` on `body`), with exceptions written in mixed case: the Main Menu credits, the Intro note, which becomes "Grab your best headphones first ;)" (both as in `MAIN MENU.png` and `INTRO.png`), and (Phase 47, `GAMEPLAY TIPS.png`) the Gameplay tips. The text is written in the JSX or the level file exactly as it should appear, and each of these elements opts out with `text-transform: none`. The font has lowercase glyphs, and it's monospaced, so the note keeps its width and the Intro layout doesn't change.

- **How To Play screen (cycle 3):** a third Main Menu button, `HOW TO` (below SETTINGS), opens a How To Play screen (`HOW TO PLAY.png`, `MAIN MENU.png`) with the game's instructions, an example drawing of the arena and a `<<< BACK` button. It's a fourth screen over the menu background animation: it's added to `MENU_BACKGROUND_SCREENS` in `App.jsx`, so it's the same `MenuBackground` instance and the animation never restarts when moving between the Main Menu and this screen (same rule as Level Select and Settings). The menu track keeps playing. The text's source is `docs/game-instructions.md` (seven paragraphs, blank-line separated; `MOUSE` and `GAMEPAD` are heading lines), and the screen renders those same paragraphs. **The single-line rule is unbreakable for buttons only**: the instructions are multi-line, left-aligned, in mixed case, with no border (like the Intro note and the credits: the mockup wins), except the `MOUSE` / `GAMEPAD` headings, which stay uppercase. The drawing is `assets/images/HOW TO PLAY example vector.svg` (all text converted to paths; the older `HOW TO PLAY example.svg` has live text and is not used). It's inlined as a React component instead of an `<img>`, for the same reason as the logo: an `<img>` can't follow `--fg`, so it wouldn't tint in screen transitions. Its hard-coded `#000` fills and strokes become `currentColor`, and its invisible bounding `<rect>` is dropped.
- **Blinking buttons (cycle 3):** Level Select didn't show which levels of a tier were already beaten. An unlocked level still to beat now blinks its name (1 s on, 1 s off, text only). Rejected: lowercase names for unbeaten levels (breaks the uppercase rule), a filled / empty dot beside the name (no room next to the longest names), and an underline on beaten levels (cluttered once most levels are beaten). Blinking marks the pending levels, which are always few (few unlocked early on, few left late), and it's an early arcade cue (the blinking 1UP). `ENTER BOUNCERBACK` blinks too, so the first click teaches "a blinking button is the one to press next"; How To Play doesn't explain it. An activated button stops blinking so the choice is readable through the screen-out. There's no reduced-motion fallback: the game, the menu animation and the transitions don't follow that setting either, and a 0.5 Hz text blink isn't the motion it protects from. Implementation: `Button` always wraps its text in a `button__label` span, and its `blinking` prop adds a class whose `opacity` reads a registered `--blink` property, animated once per menu on `.menu__items`, so every blinking text on a screen shares one clock (the screen and its direct children can't hold it: the screen transitions' animations replace theirs).

### Game controller (cycle 3)
- The terms, the controls and how controllers are read are in `docs/game-controller.md`, the source of truth. The decisions below are about how this plan implements them.
- **Choices made with the user:** the sticks share the paddles with the mouse and touch, like two more fingers: either stick places the next paddle, and the paddle limit (first in, first out; the level's `paddles.count` from Phase 56) decides which one goes (Phase 33). *(Phases 30–32 first gave each stick its own paddle; in play that proved confusing, since both sticks can reach the whole ring.)* Also: the selection's double border is line, gap, line (graphical-specs "Game controller selection"); the right face button does nothing on Game Over / You Win!; the Intro is left out, because controller input can't unlock audio.
- **Menus (React domain):** a small DOM module started once by `App.jsx` (`src/input/menuNavigation.js`). It polls in its own `requestAnimationFrame` loop only while a controller is connected, toggles a class on the selected button and activates it with `element.click()`, so the screens' `onClick` handlers and `navigate()`'s transition guard work unchanged. No React state; the only per-screen wiring is two data attributes. Moving is spatial (nearest button in the pushed direction), so the same code handles the vertical menus and the Settings rows.
- **Press feedback (Phase 35):** a mouse click shows the button pressed (`:active`, inverted) until release, and the browser only clicks on release. The controller first clicked on the press, with no feedback, and the screen-out started on the same frame. Now the controller follows the mouse: the pressed look while held, activation on release, and a press can be cancelled. It reuses the mouse's style, so both inputs look the same. *(A short flash with activation still on the press was rejected: it would play during the screen-out, fading and tinting with it.)*
- **Selected item look:** drawn with `outline` (`outline-offset` = one border width) in `--fg`, so the layout doesn't move and it tints with the screen transitions; drawn inward (negative offset) on the Settings `-` / `+` steps, which share their borders with the volume control.
- **Gameplay (PixiJS domain):** `GameEngine` owns its own reader and polls it in `app.ticker`, so pausing (ticker stopped) also stops controller input. The paddle logic is shared by the pointer and the sticks, keyed by input (the `pointerId` or the stick's name).

### CRT effect (cycle 3)
- **Goal:** the game arena looks like an old CRT screen: a zoom blur (Resolume Avenue's Radial Blur as the reference, mixed at 15%), then curved glass, chromatic aberration, scanlines, a phosphor mask and a vignette (graphical-specs "CRT effect (game arena)"). Bloom, noise and flicker are left out for now; the pipeline leaves room for them.
- **Choices made with the user:** the HUD stays in React, flat and sharp on top of the canvas: it's not curved, blurred or scanlined (moving it into PixiJS was considered and rejected for now). Only the game arena gets the effect. The effect is its own module, reusable outside the game. Every numeric value is a named constant, since the final values are an aesthetic choice made by eye. The module is documented as a learning resource (`docs/crt-effect.md`).
- **Its own module:** `src/effects/crt/`, PixiJS only, with no game logic and no import from `src/game/`. Anything that renders with a PixiJS v8 WebGL renderer can use it: give it a container to process and add its output to the stage. `GameEngine` is its first user.
- **Constants:** every tunable number lives in `src/effects/crt/crtSettings.js` (one exported, frozen `CRT_SETTINGS` object, each value commented with its unit, what it does on screen and a sensible range). A user of the module can override any value when creating it. No numbers are hard-coded in the shaders: they arrive as uniforms, except the blur's sample count, which GLSL needs as a constant loop bound and is written into the shader source when it's built.
- **Pipeline (three passes per frame):**
  1. **Scene:** the arena is rendered into a full-screen `RenderTexture` (MSAA on, so the thin lines keep their antialiasing; resolution `min(devicePixelRatio, MAX_RESOLUTION)`), cleared with the arena's background color. The arena container is no longer on the stage: the engine renders it here itself.
  2. **Zoom blur:** a full-screen shader reads the scene texture and writes a low-resolution blur texture (`BLUR_TEXTURE_HEIGHT` px tall, whatever the device). Each pixel averages `BLUR_SAMPLES` points on the line toward the blur center, up to `BLUR_STRENGTH` of the way, starting from a fixed per-pixel random offset (jitter) so the samples don't show as stacked copies.
  3. **CRT:** a full-screen shader on the stage (the only thing on the stage) draws the canvas. For each pixel it first bends the coordinates (curvature), then reads the scene (with chromatic aberration) and the blur at the bent position, mixes them (`BLUR_MIX`), then applies scanlines, the mask, the vignette, the brightness gain and the black outside the glass. Blurring before bending makes the streaks curve with the glass, like on a real CRT.
- **Why full-screen quads, not PixiJS `Filter`s:** a filter works on its target's bounds, with padding and coordinate conversions (`uInputSize`, `uOutputFrame`) that are hard to follow and a known source of offset bugs. Here every pass covers the whole screen, so each pass is a `Mesh` with a custom `Shader` drawing one rectangle that fills the screen, with plain 0–1 texture coordinates. Easier to read and to learn from. It also skips the filter system's temporary textures.
- **One CRT shader, not a chain:** each extra full-screen pass costs a full-resolution read and write, which adds up on phones at high pixel density. All the CRT steps share one pass. The blur is its own pass because it runs at a much lower resolution.
- **WebGL only:** the shaders are written in GLSL, so the engine asks PixiJS for WebGL (`preference: 'webgl'`; it's already the v8 default, now explicit).
- **Curvature preserves angles:** the bend moves every point straight away from the screen center (`p × (1 + CURVATURE × r²)`, with `r` measured in pixels, 1 at the corners), so directions from the center don't change, only distances. The core sits at the screen center, so a paddle placed at an angle stays at that angle. Formulas that bend x and y separately (common in shader examples) would skew angles, so they're not used.
- **Input mapping:** the shader decides, for each screen pixel, which scene point it shows, so mapping a touch to the scene point under it is the same formula run in JavaScript, with no inverse to solve. `curvature.js` holds the JavaScript copy, and the shader and the copy name each other in a comment so they're changed together. `GameEngine` maps `event.global` through it before `playfield.toLocal()`. Controller sticks give angles directly and need nothing.
- **Cost (ballpark, mid-range phone):** scene render ~0.3–1 ms of GPU time (mostly the MSAA resolve), blur ~0.3–0.8 ms, CRT pass ~1–2 ms with the resolution capped at 2×: about 2–4 ms of a 16.6 ms frame. CPU cost is negligible (two extra draw calls and a few uniforms a frame).
- **Switches:** `POST_PROCESSING_ENABLED` in `GameEngine.js` (named `CRT_ENABLED` until Phase 39) turns the whole effect off: the arena goes back on the stage and renders as before, which makes it easy to compare. `BLUR_ENABLED` in `crtSettings.js` turns off only the zoom blur and keeps the CRT layers. From Phase 39, `CRT_ENABLED` in `crtSettings.js` turns off only the CRT layers and keeps the blur; the game sets it from the Settings "OLD TV" switch. With it off the blur pass doesn't run and its texture isn't created, so it costs nothing (not just a 0% mix). Like the other settings, a user of the module can override it.

### CRT on the menus (cycle 3)
- **Goal:** the OLD TV switch also covers the screens that show the menu background animation (Main Menu, Level Select, Settings, How To Play). The animation and the Main Menu logo are shown through the same CRT effect as the game arena; the buttons, texts, credits and the How To Play screen's instructions and example drawing stay flat and sharp on top, as the HUD does over the arena (they're screen elements, which take part in the CSS screen transitions).
- **Choices made with the user:**
  - **The background goes through PixiJS** (rather than a CSS/SVG imitation of the effect): Lottie's **canvas** renderer draws the animation into an off-screen canvas, uploaded as a texture into a PixiJS scene processed by the existing `PostProcessing` + `CrtEffect`. `lottie_canvas` keeps expression support (the animation needs `loopOut('cycle')`); `lottie_light_canvas` doesn't, so it can't be used.
  - **The logo goes inside the tube**, drawn in the same PixiJS scene as the background (rather than staying flat in the DOM or imitating the effect in CSS). Its blink and its part in the screen transitions move to PixiJS with it.
  - **All four menu-background screens** get the effect, not only the Main Menu: the animation is one instance shared by the four screens, and it must never restart or jump between them.
  - **The OLD TV switch controls it**, like on the arena (off by default). Switching it on the Settings screen changes the background immediately.
  - **PixiJS is used even with the effect off:** one Lottie player, one logo, and no live hand-off between two players when the switch changes. With OLD TV off the menus must look as they did before (now drawn by the canvas renderer and PixiJS instead of SVG).
  - **Configurable glass-edge color:** what's outside the curved glass (the rounded corners and edges) is a new CRT setting, `EDGE_COLOR`, **black by default** — on the menus too, like a TV's frame around the light picture.
- **Its own module, `src/menu/`:** `MenuScene.js` owns the menu's PixiJS application, the Lottie animation, the logo and the post-processing; it's the menus' counterpart of `GameEngine`. `MenuBackground.jsx` stays its React mount point, in the same place in `App.jsx`, so it lives across the four screens as today. React only sends it low-frequency calls (OLD TV changes, the logo's state on screen changes, the logo's box on resize): no frame-by-frame state crosses the boundary.
- **The menu's own CRT values:** the effect is reused unchanged, created with overrides from `src/menu/menuSettings.js`. Needed because the arena's values are tuned for a black picture: the brightness gain would clip the `#D8D8D8` background and the animation's light-grey and white lines all to white, and the tone-on-tone animation would disappear. Only the values that must differ are overridden (brightness, vignette), so the menus and the arena look like the same TV. No zoom blur on the menus (there's no core for it to radiate from).
- **The logo's layout stays in CSS:** the Main Menu keeps an invisible box in the logo's place (`.main-menu__logo`, same size and margins, with the `role="img"` / `aria-label`), and the PixiJS logo is drawn over the box's measured position. The 1518px / 182px layout isn't duplicated in JavaScript, and the logo + buttons group stays laid out by CSS.
- **Colors from the CSS tokens:** `MenuScene` reads `--color-black`, `--color-white`, `--color-white-bg`, `--color-tint-yellow` and `--color-tint-red` once at mount (`getComputedStyle(document.documentElement)`), so `index.css` stays their only source.
- **Transition timing is duplicated, on purpose:** the logo's screen-out (1 s fade; tint to yellow from 0.5 to 0.75 s, then to red until 1 s; the shake from 0.875 s) and screen-in (0.5 s fade) are tweens in PixiJS with the same timings as the CSS keyframes. Each constant names its keyframe in `index.css` in a comment, and the keyframes name `MenuLogo.js` back, so they're changed together (as `curvature.js` and `crt.glsl` are). Mirroring the CSS by reading the invisible box's computed style every frame was considered and rejected: it forces a style recalculation every frame and couples PixiJS to the DOM's animation state.
- **Cost:** new on screens that cost almost nothing today. Per frame: the canvas renderer draws the animation on the CPU, one full-screen texture upload (only when Lottie drew a new frame), and with OLD TV on, the CRT's final pass (as on the arena, minus the zoom blur). If a phone struggles, `menuSettings.js` can lower the off-screen canvas' resolution: the CRT softens the picture anyway.

### Storytelling: end-of-level interstitials (cycle 3)
- **Goal:** the first storytelling element: a level can show a picture after it's won or lost, before the result screen (Phases 57–58). Named per outcome in the level file (`youWinInterstitial`, `gameOverInterstitial`); missing or blank means no picture and the level ends as before.
- **Choices made with the user:**
  - **Drawn in the PixiJS game canvas**, not in React, so it follows OLD TV like the arena: same bloom and CRT values (the pictures are deliberately low fidelity, so they need none of their own), never the zoom blur, which radiates from the core.
  - **Cut in and cut out.** The picture replaces the arena at once and the HUD goes with it; on continue, the result screen replaces it at once and plays only its screen-in (a screen-out would leave the picture standing still for a second with nothing animating).
  - **Press to continue**, after a short input lock so a stray tap at the end of the level doesn't skip it. On the release, like the menus, so the release can't reach the result screen's buttons. Taps, clicks, the menus' activate buttons (bottom face button, RT) and Enter / Space.
  - **Contain fit**: the whole picture is always visible, with black bars where the screen's shape differs. Pictures may hold text, which cropping could cut.
  - **Complete silence** while it's shown: the level track and the SFX are cut when it appears. How the result ambiences are used will be reconsidered later.
  - **An exception to "no images"**: the pictures are bitmaps, but they come between player actions, after the level has ended; gameplay stays vector only.
- **The result is saved when the picture appears**, not on continue: the engine emits the outcome then (with `interstitial: true`), and React registers the score and the win but holds the result screen until `onContinue`. Closing the app on the picture loses nothing.
- **The pictures are the engine's own textures**, loaded with an `Image` when the level mounts and destroyed with the engine, not through PixiJS' `Assets` cache (the plan said `Assets.load()` / `Assets.unload()`). With the shared cache, an engine torn down late (React StrictMode's double mount in development, the delayed WebGL teardown) would unload the texture the next engine is using.
- **Checked twice:** the schema's `pattern` rejects names with a folder or not ending in `.png` (the in-game checker learned `pattern`), and both the loader and `npm run validate:levels` check that the file exists in `assets/interstitials/`, which a schema can't express.

### Desktop build (Steam)
Planned in `docs/desktop-build.md`, which holds the details.
- **Electron as the desktop wrapper**, not Tauri: Electron bundles its own Chromium, so WebGL, the GLSL post-processing and the Gamepad API behave the same on Windows, Linux (and the Steam Deck) and macOS, and the same as in the browser where the game is developed. Tauri uses each OS's own WebView (WebKitGTK on Linux), which differs per OS and is riskier for the shaders and controllers. Electron's larger download is accepted.
- **Minimum Steamworks scope:** launching through Steam, the overlay (with the game pausing when it opens) and a default Steam Input controller configuration, so the existing Gamepad API handling keeps working unchanged. Achievements, stats, leaderboards, Steam Cloud, Rich Presence, the Steam Input API, Workshop and the rest are listed as nice to have in `docs/desktop-build.md`, not planned.
- **Test build choices (Phase D1):** electron-builder (one config for Linux, Windows and macOS later); Electron 44 pinned to an exact version (45.0.0 was days old); a `.tar.gz` of the unpacked app rather than an AppImage (keeps the executable permissions on any USB stick, needs no FUSE on the Deck, closest to a Steam depot); built on the Mac. The game is served through a custom `app://bouncerback/` protocol, not `file://`, so fetch / XHR (Howler, the hashed asset URLs) work as on the web site and `localStorage` has one fixed origin. X11 is forced on Linux: the Deck's Game Mode runs games through Xwayland, and the overlay approach planned later needs X11. Only `dist/`, `electron/` and `package.json` are packed: the game is fully bundled by Vite, so no `node_modules` ship.
- **Steamworks stays in Electron's main process**, behind a small preload bridge; the game only exchanges low-frequency messages with it, and the web and mobile builds run without it.
- **The preload bridge (Phase D2)** is `window.bouncerbackDesktop`, and its presence is how the game knows it's a desktop build: no build flag, and no sniffing of the user agent or the `app:` protocol. Its first message is quit.
- **EXIT GAME (Phase D2)** quits like any Main Menu button leaves: the screen-out plays and the music fades, then the main process quits (`app.quit()`, not `window.close()` from the page: the main process will also have to shut Steamworks down). No confirmation: nothing is lost by quitting from the Main Menu. The fourth button takes its room from the gaps (a third of a button's height each) and the logo gap, so the rest of the Main Menu doesn't move.

- **The Escape key (Phase D3)** is desktop only: on the web the browser keeps it (leaving fullscreen, among others). It goes back to the Main Menu from the other menus and the result screens, and never quits (that's EXIT GAME's job). In a level it pauses, and resumes on the Pause Overlay, like `P` and the controller's menu button; it leaves the level only from the Gameplay Tips, where nothing is lost yet, so a stray press during play can't lose a game. Its own ref in `GameScreen` (`escapeRef`), separate from the Android back button's, which still does nothing on the tips.
- **ENTER BOUNCERBACK with the controller (Phase D4)** on desktop only. The Intro ignores the controller on the web because browsers don't unlock audio on controller input; Electron needs no user gesture for audio (`autoplayPolicy` set explicitly in `electron/main.js`), and the Steam Deck must be playable with its built-in controls alone (Steam Deck Verified). Browsers only expose a controller after one of its buttons is pressed, and that press never counts as a press, which would make the player press twice; so on the Intro the connecting press (bottom face button or RT) enters, on release. Only a button marked `data-gamepad="connect-press"` takes it: elsewhere, picking up the controller must not activate anything (on the Main Menu it would start PLAY). A press during the Intro's screen-in, or a tap released before the first poll, is missed and the player presses again: accepted.
- **The Windows test build (Phase D5)** is a `.zip` of the unpacked app, x64 only, unsigned, built on the Mac. A zip rather than an installer or a portable `.exe`: Steam installs a depot's folder itself, and a portable `.exe` unpacks itself to a temporary folder on every launch. x64 only, because that is Steam's Windows build (Windows on ARM runs it emulated). Built on the Mac because electron-builder 26 edits the `.exe` in JavaScript, so no Wine or Windows machine is needed. Unsigned until a certificate is bought. With no Windows PC at hand it is tried under CrossOver, which only shows whether the build is sound, not how it performs on Windows; a real Windows PC test stays open. The executable is `Bouncerback.exe`, the product name as Windows apps usually are, unlike the Linux build's lowercase `bouncerback`.

### VFX vocabulary
`level-file-schema.json`'s `vfx[].name` and `graphical-specs.md`'s "optional effects" have no concrete identifiers yet. Two are introduced for cycle 2: `palette_invert` (black/white swap) and `glow_pulse` (paddle glow). Level files can reference these by name in their `vfx` timeline. The "one life left" state is not a timeline vfx: per graphical-specs "Visual feedback", the gameplay background fades to dark red (`#550000` from Phase 34) over 0.5 s, driven directly by game state regardless of the level's own vfx list.

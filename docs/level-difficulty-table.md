# Level difficulty table

A table that compares every level's difficulty, duration and maximum score, to check that the difficulty goes up from level to level. It is always generated by a script from the level files, never written by hand, so it never goes stale.

## How to generate it

```
npm run level:table
```

The script is `scripts/level-difficulty-table.js`. It reads every `src/levels/levelN.json`, in the order of `N`, and prints a Markdown table plus one footnote. When asked for a table summarizing the levels' difficulty, run it and present its output as it is (then add the observations: see "Reading the table"). Don't change the layout or recompute anything by hand: to change a column, edit the script and this doc together.

The script takes the point formulas from `src/game/scoring.js` and the charge limits and the supercharged atom's speed factor from `src/game/entities/Atom.js` (`MAX_CHARGE`, `SUPERCHARGED_CHARGE`, `SUPERCHARGED_SPEED_FACTOR`), so a change to any of them shows up in the table. Nothing else is restated here: the level files and those two files are the only source of truth for the values.

## Columns

Every value is derived from the level file. Let `spb` (seconds per beat) be `60 / bpm`.

| Column | Meaning | How it is calculated |
| :--- | :--- | :--- |
| # | Level number | The `N` in `levelN.json`. It is also the score multiplier |
| Name | Level name | `name` |
| Tier | Level Select row | `tier` |
| Duration | Length of the level in seconds | `duration * signature * spb` (bars * beats per bar * seconds per beat) |
| BPM | Tempo | `timeSignature.bpm`. The signature is added in parentheses when it isn't 4/4, for example `(3/4)` |
| Mechanics | Additional game mechanics | The `additionalGameMechanics` names shortened: `atom capture` is "capture", `charged atom hold` is "hold", `supercharged atom` is "super". Empty is "core only" |
| Atom travel | Time an atom takes to go from the core to the ring: the player's reaction time | `atoms.travelTime * spb` |
| Spawn interval | Time between atoms | `atoms.barsInterval * signature * spb` |
| Atoms/min | How dense the level is | `60 / spawn interval` |
| Lives | Lives at the start | `lives` |
| Paddles (count × life) | How many paddles can be set at once, and how long each one lasts | `paddles.count` (2 if missing) and `paddles.duration`, in seconds |
| Max score (approx.) | Ceiling of the score, see below | See below |
| Paddle demand | How much work the level asks for at its end, see below | See below |

### Max score

The score ceiling is an estimate under a fixed set of assumptions, so that levels can be compared with each other. It is not a promise that the number can be reached.

Assumptions:

* One atom spawns in each spawn interval, `floor(duration / barsInterval)` atoms in all, and every one spawns in the middle of its interval (the game picks a random moment).
* The first bounce of an atom is one atom travel after its spawn, and then it comes back to the ring once per round trip (two atom travels). It is bounced every time.
* With `atom capture`, each bounce adds a charge, up to `MAX_CHARGE`. Without it the charge stays at 1.
* No atom is captured: containing an atom at the end scores more than capturing it. No lives are lost. `charged atom hold` points are left out (see below).
* With `supercharged atom`, one more atom appears at half the level's time, with a fixed charge of `SUPERCHARGED_CHARGE`, and travels `SUPERCHARGED_SPEED_FACTOR` times faster.

The ceiling is the sum, using the formulas of "Score" in `docs/game-rules.md` (and `src/game/scoring.js`):

1. **Bounce points** of every bounce of every atom, at the charge the atom has when it hits the paddle.
2. **Containment points** of every atom at the end, at the charge it has reached.
3. **Time bonus**, from the level's initial timer value in tenths of a second.
4. **Lives bonus**, with all the lives left.

Hold points are left out because they depend on how long the player keeps an atom held, which has no natural ceiling. They are worth, per second, `POINTS_PER_SECOND * level * atom charge` (`src/game/chargedAtomHoldSettings.js`), so levels with `charged atom hold` can score clearly more than the table says.

The score is shown rounded: in thousands (`K`), or in millions (`M`) from a million up.

### Paddle demand

The number of bounces per second the player needs to keep up at the end of the level, if no atom is ever captured. It measures how much work the level piles up.

Atoms never leave the ring unless they are captured or escape, so every atom spawned is still in play at the end and needs a bounce every round trip. The demand is then the number of atoms divided by the round trip time:

```
atoms / (2 * atom travel)
```

With `supercharged atom`, one more atom is added whose round trip is shorter by its speed factor, so it adds `SUPERCHARGED_SPEED_FACTOR / (2 * atom travel)`.

Capturing atoms lowers the real demand, so this is the worst case, not what a player sees. It is useful to compare levels, and because it grows with both the density and the length of a level.

## Reading the table

What to check for the progression to go up (a recommendation for the comments that go with the table, not a rule of the game):

* **Pace:** atom travel and spawn interval shrink (or atoms/min grow) from level to level, and lives and paddle life do not grow without a reason.
* **Length:** the level gets longer, or denser, but not both easier on one side and shorter on the other.
* **Mechanics:** new mechanics are only added at the first level of a tier (see "Additional game mechanics" in `docs/game-rules.md`), so the mechanics should be the same across a tier.
* **Ceiling and demand:** both should go up. A drop is a sign that a level is out of place, or that it is much shorter than its neighbours.
* **Tiers:** the levels of a tier should be similar in difficulty, and every tier harder than the one before.

### Phase 30 — Gamepad API fundamentals
- New `src/input/gamepad.js`, pure JS:
  - Constants: `STICK_ENGAGE = 0.75`, `STICK_RELEASE = 0.35`, `TRIGGER_THRESHOLD = 0.5`, and `BUTTONS` (`A`, `B`, `LT`, `RT`, `L3`, `R3`, `UP`, `DOWN`, `LEFT`, `RIGHT` → standard-mapping indices) as an enum-like object.
  - `watchGamepads(onChange)`: listens to `gamepadconnected` / `gamepaddisconnected` and calls `onChange(hasGamepad())`; returns an unsubscribe function. `hasGamepad()`: whether at least one `standard` controller is connected. Both are safe where the API is missing (`navigator.getGamepads?.()`, e.g. an insecure context): no controller, no errors.
  - `class GamepadReader`, one per consumer (the menus and each `GameEngine` have their own, so their press detection never interferes):
    - `poll()`: reads `navigator.getGamepads()` and picks the active controller (see `docs/game-controller.md`). Stores each button's state (digital buttons: `pressed`; LT / RT: `value ≥ TRIGGER_THRESHOLD`) and keeps the previous poll's. Updates each stick's state: `engaged` turns on at magnitude ≥ `STICK_ENGAGE` and off below `STICK_RELEASE`; `angle` = `Math.atan2(y, x)`, updated only while the magnitude is ≥ `STICK_ENGAGE`; `justEngaged` is true on the poll where `engaged` turns on.
    - `isDown(button)`, `wasPressed(button)` (down now, up on the previous poll), `stick('left' | 'right')` → `{ engaged, justEngaged, angle }`.
    - `reset()`: the next poll only records the state (no presses, no `justEngaged`). Also applied to the first poll after creation and whenever the active controller changes, so a button already held never counts as a press.
- No other file changes. Nothing is visible yet: check it on the dev server with a temporary `console.log` of the reader's state (removed before committing), then through Phases 31–32.
- `docs/project-structure.md` gets the new `src/input/` folder.

### Phase 31 — Menu navigation
- New `src/input/menuNavigation.js` (DOM only, like `Logo.jsx`'s blink: it toggles a class, no React state):
  - `startMenuNavigation(root)` → `stop()`. `root` is the `.screen-transition` wrapper. It owns one `GamepadReader`, runs a `requestAnimationFrame` loop only while `hasGamepad()` (started and stopped through `watchGamepads`), and listens to `pointerdown` on `window` (capture phase) to leave controller mode. A `gamepadconnected` turns controller mode on; the last controller disconnecting stops the loop and leaves controller mode. `stop()` cancels the loop and removes the listeners.
  - Selectable items: `root.querySelectorAll('.screen button:not([data-gamepad="ignore"])')`, in DOM order.
  - Every frame: `poll()`; drop the selection if its element is no longer in the document (the screen changed); in controller mode with nothing selected, select the first item, if any. Then, if `root` has the `screen-transition--out` or `screen-transition--in` class, stop here (input is ignored during transitions; the poll above keeps press detection up to date). Otherwise:
    - Direction: d-pad `wasPressed`, or the left stick's `justEngaged` reduced to 4 directions (its dominant axis). With nothing selected, it turns controller mode on and selects the first item. Otherwise it moves to the nearest item in that direction: candidates are items whose center lies beyond the selected item's center on that axis; the score is the distance along that axis + 2 × the offset across it, lowest wins, ties go to DOM order. No candidate: nothing happens.
    - `A` or `RT` `wasPressed`: with an item selected, `item.click()`; with nothing selected, select the first item (it doesn't activate anything).
    - `B` `wasPressed`: `root.querySelector('.screen [data-gamepad="back"]')?.click()`.
    - Any of the above turns controller mode on.
  - Selecting an item moves the `gamepad-selected` class to it; leaving controller mode removes it and clears the selection.
- `src/App.jsx`: a ref on the `.screen-transition` wrapper and a mount-only `useEffect(() => startMenuNavigation(wrapperRef.current), [])` (returns `stop`, so StrictMode's double effect is clean). No other change: activation goes through each button's `onClick`, so `navigate()` and its transition guard work as for a click.
- `src/screens/IntroScreen.jsx`: `data-gamepad="ignore"` on the `ENTER BOUNCERBACK` button (`Button` already spreads extra props), with a comment: controller input can't unlock audio (see `docs/game-controller.md`).
- `src/screens/LevelSelectionMenuScreen.jsx`, `src/screens/SettingsMenuScreen.jsx`: `data-gamepad="back"` on the `<<< BACK` button.
- `src/index.css`, new `/* Game controller selection */` block after `/* Settings: volume dual-button */`:
  - `.button.gamepad-selected, .volume-control__step.gamepad-selected { outline: var(--border-width) solid var(--fg); outline-offset: var(--border-width); }`. Two classes, so it wins over `.button:focus-visible`'s `outline: none`. `var(--fg)` rather than `currentColor`: a focused (inverted) button's text is `--bg`.
  - `.volume-control__step.gamepad-selected { outline-offset: calc(-2 * var(--border-width)); }`: inside the step, leaving a one-border gap to the control's outer border and to the label's side border.
- Game Screen, Game Over, You Win!: no change. The Game Screen has no buttons, so the menu navigation does nothing there (the engine handles the controller); the result screens' TRY AGAIN / MAIN MENU are reachable, and they have no `data-gamepad="back"`, so the right face button does nothing there.

### Phase 32 — Gameplay
- `src/game/entities/Paddle.js`: a `stick` property (`'left'`, `'right'` or `null`) that tells which stick set the paddle. `start()` resets it to `null`, so a paddle reused from the pool never keeps an old owner. *(Removed in Phase 33.)*
- `src/game/GameEngine.js`:

  - Pull the paddle logic out of the pointer handlers into methods keyed by an input id (the `pointerId`, or `'left'` / `'right'` for the sticks), so both inputs share it; `draggedPaddles` holds both kinds:
    - `startPaddleDrag(input, angle)`: today's `onPointerDown` paddle part (release any paddle already dragged by that input, take one from the pool, `start(angle)`).
    - `dragPaddle(input, angle)`: `setAngle`.
    - `setPaddle(input, stick = null)`: today's `onPointerUp`. With a `stick`, it first releases the active paddle with the same `stick` (each stick owns one paddle), then tags the new one, activates it and pushes it; the `MAX_ACTIVE_PADDLES` FIFO stays as it is. *(Phase 33 removes the per-stick ownership: `setPaddle(input)` only.)*
    - The pointer handlers call these; their behavior doesn't change.
  - `update()`: `this.gamepad.poll()` every frame, before the state switch (so press detection stays up to date during the start delay and the core collapse), then `this.handleGamepad()` only in `STATE.PLAYING`.
  - `handleGamepad()`:
    - Capture: if any of `A`, `LT`, `RT`, `L3`, `R3` `wasPressed`, call `captureAtCore()` once.
    - For each stick: `engaged` → `startPaddleDrag` the first time, then `dragPaddle` with its `angle`; not `engaged` while it's dragging a paddle → `setPaddle(name, name)`. The stick's angle maps straight to the paddle angle: both have y pointing down.
  - `togglePause()`: on resume, `this.gamepad.reset()`, so a button pressed during the pause doesn't fire on resume. While paused the ticker is stopped, so nothing is polled.
  - `clearPaddles()` already clears every dragged paddle (sticks included) at the core collapse and on Game Over. Afterwards `handleGamepad()` isn't called, so a stick still pushed doesn't bring one back.

### Phase 34 — Paddle replacement warning

- `src/game/entities/Paddle.js`:

  - `setWarning(on)`: stores `this.warning` and, only when it changes, sets `this.view.tint` to `WARNING_COLOR` or `0xffffff`. The paddle is drawn white, so the tint makes it red without a redraw (the same approach as the atom pulses). The lifetime fade keeps working through `view.alpha`.

  - `PaddleFlash` is a separate `Graphics`: the echo stays white.
- `src/game/GameEngine.js`:
  - `updatePaddleWarnings()`: `const pushedOut = this.activePaddles.length + this.draggedPaddles.size - MAX_ACTIVE_PADDLES`, then `this.activePaddles.forEach((paddle, i) => paddle.setWarning(i < pushedOut))`. `activePaddles` is ordered oldest first (push / shift), so the first ones are the ones the FIFO removes. A negative or zero count warns none, and the count can't exceed the active paddles that exist.

### Phase 36 — Last life zoom
- Losing the last life freezes the playfield, then zooms 8× on the last atom and where it crossed the ring (see "Last life zoom" in the Gameplay Decisions, graphical-specs "Visual feedback" and game-rules "Game over condition"). Lives, scoring and the Game Over screen don't change. *(Revised after the first version: see the Decision.)*
- New `src/game/geometry.js`: `circlePoints(radius, segments = CIRCLE_SEGMENTS)` returns a flat `[x0, y0, x1, y1, …]` list for `Graphics.poly()`. `CIRCLE_SEGMENTS = 128`: at 8× the ring's sides are well under 1 px off a true circle on screen, and an atom's much less.
- `src/game/entities/Atom.js`: the constructor draws `.poly(circlePoints(ATOM_RADIUS))` instead of `.circle()`. Fill, tint and scale work as before.
- `src/game/entities/ContainmentRing.js`: `draw(radius)` strokes `.poly(circlePoints(radius))` (closed) instead of `.circle()`. The start animation redraws it as before.
- `src/game/entities/AtomPulse.js`, `AtomEmitter.js`, `PaddleFlash.js`, `Paddle.js`: no change. The pulses and the core are near the center, far from the focus, and paddles are hidden at the loss. An echo could still be in view but lasts 0.2 s at most.
- `src/game/GameEngine.js`:
  - Constants: `LAST_ESCAPE_TIME = 0.5`, `ZOOM_SCALE = 8`, `ZOOM_TIME = 0.5`, `ZOOM_HOLD = 1`. `GAME_OVER_DELAY` becomes `LAST_ESCAPE_TIME + ZOOM_TIME + ZOOM_HOLD` (1 → 2 s).
  - Camera: `this.zoom = { scale: 1, focusX: 0, focusY: 0, offset: 1 }` in the constructor (`offset` is the share of the focus point's normal offset from the screen center still left). `layout()` uses it: with `base = min(width, height) / REFERENCE_SIZE` and `s = base × zoom.scale`, `playfield.scale = s` and `playfield.position = (width / 2 + focusX × base × offset − focusX × s, height / 2 + focusY × base × offset − focusY × s)`. At `scale 1, offset 1` that's the current centered layout, so nothing changes before the loss, and resizing during the zoom keeps the framing.
  - `checkContact()`: when an escape takes `lives` to 0 and `this.lastAtom` isn't set yet, store `this.lastAtom = atom`. With several escapes on the same frame, the first one to reach 0 is the one zoomed on; the others escape and then freeze.
  - `updateLost(dt)`: replaces `updateVanishingAtoms(dt)`. Game Over is emitted at `GAME_OVER_DELAY` as today. The atom stays in `this.atoms` at full opacity until the engine is destroyed.
  - `updateVanishingAtoms()` stays for the core collapse, unchanged.
  - Pause (`P`) freezes the zoom and the slow motion through `app.ticker`, as before. Try Again builds a new `GameEngine`, so the camera starts at 1× without a reset.
- `src/screens/GameScreen.jsx`, HUD, `soundManager.js`: no change. The HUD stays on top at its normal size; the screen-out starts 2 s after the loss (was 1 s).

### Phase 37 — Post-processing pipeline & zoom blur
- New module `src/effects/crt/` (PixiJS only; no import from `src/game/`):
  - `crtSettings.js`: `CRT_SETTINGS`, frozen, every value with a comment (unit, effect on screen, range). Starting values for this phase:
    - `MAX_RESOLUTION = 2`: cap on the device pixel ratio for the scene texture and the canvas.
    - `BLUR_ENABLED = true`: the zoom blur's switch (see "Switches" in Decisions).
    - `BLUR_TEXTURE_HEIGHT = 360`: height of the blur texture in pixels; its width follows the screen's aspect ratio.
    - `BLUR_SAMPLES = 24`: points averaged per blur pixel (built into the shader source).
    - `BLUR_STRENGTH = 0.38`: streak length as a share of the distance to the center (measured on the Resolume reference).
    - `BLUR_MIX = 0.15`: blur opacity over the scene.
    - `BLUR_JITTER = 1`: per-pixel random sample offset, 0–1 (0 shows the stepping, for comparison).
  - `fullscreen.vert.glsl`: shared vertex shader. The rectangle goes from (0, 0) to (1, 1) and the mesh is scaled to the screen; the shader places it with PixiJS's projection (`uProjectionMatrix × uWorldTransformMatrix × uTransformMatrix`) and hands the fragment shaders a 0–1 `vUV`. *(Planned as a straight pass-through to clip space; changed because WebGL stores render textures upside down compared to the canvas, and PixiJS's projection already handles that for every target.)*
  - `zoomBlur.frag.glsl`: the blur pass (pipeline step 2). Uniforms: `uScene`, `uCenter` (0–1), `uStrength`, `uJitter`. The jitter is a fixed hash of the pixel position, the same every frame, so it doesn't sparkle.
  - `crt.frag.glsl`: the final pass. In this phase it only mixes the scene and the blur (`mix(scene, blur, uBlurMix)`); Phase 38 adds the CRT steps. The blur read and mix are wrapped in `#ifdef BLUR`, defined in the source when `BLUR_ENABLED` is on. With the blur off, the shader has no blur texture to read and the step doesn't exist.
  - `CrtEffect.js`: the PixiJS glue, the module's only public entry point.
    - `new CrtEffect(renderer, overrides = {})`: merges the overrides over `CRT_SETTINGS`, creates the scene texture (`RenderTexture.create({ …, antialias: true })`), the blur texture and mesh only when `BLUR_ENABLED` is on, and the CRT mesh, so up to two full-screen meshes (`Mesh` + `Geometry` with `aPosition` / `aUV` + `Shader.from({ gl, resources })` with a `UniformGroup`). The shaders are imported with Vite's `?raw`; `BLUR_SAMPLES` is written into the blur shader's source.
    - `view`: the CRT mesh, to be added to the stage.
    - `resize(width, height)`: resizes both textures (the blur one to `BLUR_TEXTURE_HEIGHT`) and updates the size uniforms.
    - The blur mesh sits in its own `blurPass` container (never on the stage), because a container passed to `renderer.render()` is drawn as is: the mesh's scale must go on a child.
    - `render(scene, { background, center })`: renders `scene` into the scene texture cleared with `background` (`renderer.render({ container, target, clearColor })`), then (with the blur on) the blur mesh into the blur texture, with `center` (screen pixels, default the screen center) converted to 0–1. The stage render that PixiJS does after the ticker then draws `view`.
    - `destroy()`: destroys the meshes, shaders and both textures.
  - Every shader file starts with a comment explaining what the pass does and how, and comments each step, pointing to the matching section of `docs/crt-effect.md`.
- `src/game/GameEngine.js`:
  - `CRT_ENABLED = true` (`POST_PROCESSING_ENABLED` from Phase 39).
  - `app.init`: `preference: 'webgl'`; `resolution: Math.min(devicePixelRatio, CRT_SETTINGS.MAX_RESOLUTION)`.
  - `buildScene()`: a new `arena` container holds `playfield` (for the same reason: the root passed to `renderer.render()` is drawn as is, and `playfield` carries the layout's position and scale). With the effect on, `this.crt = new CrtEffect(this.app.renderer)` and only `this.crt.view` goes on the stage; the arena stays off it. With it off, the arena goes on the stage.
  - `renderArena()`: `this.crt?.render(this.arena, { background: this.backgroundColor, center: this.playfield.position })`, called at the end of `update()`. `playfield.position` is the core's screen position, so the streaks follow it during the last life zoom.
  - `updateBackground()`: with the effect on, the color goes to `crt.render()` and the renderer background stays black (shown outside the glass from Phase 38).
  - `onResize(width, height)` replaces `layout` as the renderer's `resize` listener: `layout()`, then `crt.resize()` and `renderArena()`. Resizing empties the textures, and PixiJS draws the stage right after a resize, even while paused. `layout()` stays free of it, since the last life zoom calls it every frame.
  - The delayed teardown in `destroy()` calls `this.crt?.destroy()` and `this.arena.destroy({ children: true })` (off the stage, `app.destroy()` doesn't reach it) before `app.destroy(…)`.
  - Pointer input: no change yet (no curvature in this phase). `playfield.toLocal()` works off the stage: its transform only depends on its own position and scale.
- New `docs/crt-effect.md` (the learning resource; started here, completed in Phase 38): what post-processing is, render textures and why the scene is drawn into one, full-screen quads vs filters, texture coordinates (0–1, centered −1…1, aspect correction), how a fragment shader runs once per pixel, the zoom blur step by step (the sampling line, why jitter beats more samples, why low resolution is fine), how the passes fit into PixiJS's frame, how to reuse the module elsewhere (a minimal example), and a tuning table for each constant.
- Docs: `AGENTS.md` (Documentation Map row for `docs/crt-effect.md`; the visual rules mention the CRT post-process), `docs/project-structure.md` (`src/effects/crt/` and its files), `docs/tech-stack.md` (a "Post-processing" row: custom GLSL shaders on PixiJS full-screen meshes, WebGL only).
- `GameScreen.jsx`, the HUD, the input modules: no change.

### Phase 38 — CRT layers & input mapping
- `crtSettings.js`, new starting values:
  - `CURVATURE = 0.08`: how much the corners are pushed out (0 = flat).
  - `CORNER_RADIUS = 0.03`: rounding of the glass's corners, as a share of the screen height.
  - `EDGE_SOFTNESS = 0.004`: width of the glass edge's fade to black, same unit.
  - `ABERRATION = 0.002`: red is read this share farther from the center at the corners, blue this share closer (about 2 px at the corners of a 1080p screen), growing from 0 at the center.
  - `SCANLINE_COUNT = 270`: lines per screen height, on every device (about 240p arcade; at least about 2.9 device pixels per line on a landscape phone at 2×, so they don't flicker).
  - `SCANLINE_INTENSITY = 0.3`: how dark the gap between lines gets.
  - `MASK_PITCH = 3`: width of one red-green-blue stripe group in device pixels (a whole number, so it lines up with the pixels and makes no moiré).
  - `MASK_INTENSITY = 0.12`.
  - `VIGNETTE = 0.3`: darkening at the corners.
  - `BRIGHTNESS = 1.2`: gain that makes up for the darkening.
- `src/effects/crt/curvature.js`: `warp(x, y, width, height, curvature)`, the curvature formula in JavaScript. A comment names `crt.frag.glsl`'s `warp()` as its twin.
- `crt.frag.glsl`, in this order:
  1. Center the pixel's coordinates (−1…1), measure `r²` in pixels (aspect-corrected, 1 at the corners), and bend: `p × (1 + uCurvature × r²)`.
  2. Outside −1…1 after bending, or outside the rounded corners: black, softened over `uEdgeSoftness`.
  3. Scene: red read at `p × (1 + uAberration × r²)`, green at `p`, blue at `p × (1 − uAberration × r²)`.
  4. Blur read at `p` and mixed (`uBlurMix`), only when `BLUR` is defined.
  5. Scanlines from the bent `y` (so they curve): a smooth `cos²` profile, not hard on/off lines. They fade out when a line would be thinner than 2 device pixels (small windows), instead of shimmering.
  6. Mask from `gl_FragCoord.x` (device pixels).
  7. Vignette, brightness gain, output with alpha 1.
- `CrtEffect.js`: one `UniformGroup` with every CRT uniform (plus `uBlurMix` only with the blur on), and `uAspect` updated on resize. `MASK_PITCH` is already in device pixels (`gl_FragCoord`). The scanline fade is computed in JavaScript on each resize (`scanlineFade()`: device pixels per line, smoothstep from 1.5 to 2.5) and applied to `uScanlineIntensity`, instead of per pixel. New `toScene(point)`: returns the scene point shown at a screen point (`warp()`), for input.
- `GameEngine.js`: `onPointerDown` / `onPointerMove` call `this.playfield.toLocal(this.scenePoint(event.global))`, where `scenePoint()` returns `this.crt?.toScene(global) ?? global`. The capture tap and paddle angles then follow what's on screen. Sticks: no change.
- `docs/crt-effect.md`: completed with curvature (the formula, why it preserves angles, why corners go black, why input needs the same formula and no inverse), chromatic aberration, scanlines (fixed count, the smooth profile, moiré and the thin-line fade), the phosphor mask (whole-pixel pitch), vignette and brightness, the order of the steps and why it matters, the performance budget, and the tuning table for the new constants.

### Phase 40 — Effects split
- **Why (choices made with the user):** the zoom blur's values lived in `crtSettings.js` and its mix in `crt.frag.glsl`. Each effect now owns its folder (settings, GLSL, JavaScript), so they're tidy and more effects can be added without touching the others. **No extra GPU time:** a first version chained the effects as separate full-screen passes with a texture in between (~0.3–0.8 ms more per effect on a mid-range phone); the user rejected the cost, so the effects stay in **one final pass**, as in Phases 37–38.
- **How: the final pass is composed from per-effect GLSL chunks.** Each effect provides a chunk defining `vec3 <name>(vec2 uv)`, which returns its image at `uv` and reads the previous image through `INPUT(uv)`. `PostProcessing` builds the final shader's source from a template (`postProcessing.frag.glsl`: `vec3 scene(vec2 uv)` reads the scene texture; `main()` calls `LAST(vUV)`), inserting the chunks in chain order with `#define INPUT <previous function>` before each (`scene` for the first) and `#define LAST <last function>` after them. The chain becomes nested function calls in one pass: no texture between effects. An effect can read its input anywhere and several times (the CRT's curvature and aberration), and the previous effects run at those points. Effects needing another resolution (the zoom blur's low-res blur) still run that part in `prepare()`, before the final pass; that pass reads the scene texture (`setScene()`).
- **Naming rules** (all chunks share one shader): an effect's uniforms and helper functions start with its name (`uCrtCurvature`, `crtWarp()`, `uZoomBlurMix`); chunks read the image only through `INPUT`. `PostProcessing` throws on two resources with the same name.
- New layout (see `docs/project-structure.md`):
  - `src/effects/PostProcessing.js` (was `crt/CrtEffect.js`): `new PostProcessing(renderer, effects, overrides)`. Owns the MSAA scene texture and the final pass (`view`, on the stage); merges the effects' `resources` into it; `render(scene, { background })` draws the scene and runs the effects' `prepare()`; `toScene()` asks the effects last first; `destroy()` destroys the effects too. An effect: `name`, `glsl`, `resources`, `resize()`, `toScene()`, `destroy()`, optional `setScene()` / `prepare()`.
  - `src/effects/postProcessing.frag.glsl` (new template), `postProcessingSettings.js` (`MAX_RESOLUTION`, moved out of `crtSettings.js`), `FullscreenPass.js` (the full-screen quad, used by the final pass and the zoom blur's own pass), `fullscreen.vert.glsl` (moved from `crt/`).
  - `src/effects/zoomBlur/`: `ZoomBlurEffect.js` (its own blur pass in `prepare()`; `center` property, set every frame), `zoomBlurSettings.js` (`TEXTURE_HEIGHT`, `SAMPLES`, `STRENGTH`, `MIX`, `JITTER`: the old `BLUR_*` values without the prefix, same values), `zoomBlur.frag.glsl` (moved from `crt/`, reads `uScene`), `zoomBlurMix.glsl` (its chunk).
  - `src/effects/crt/`: `CrtEffect.js` (new: uniforms, scanline fade, `toScene()`), `crtSettings.js` (the CRT values only, same values), `crt.glsl` (was `crt.frag.glsl`: now a chunk, `vec3 crt(vec2 uv)`, prefixed names, no `#ifdef BLUR` / `#ifdef CRT`, no blur mix; steps renumbered 1–6), `curvature.js` (unchanged but for the twin's name).

- `src/game/GameEngine.js`: `ZOOM_BLUR_ENABLED = true`; `buildScene()` builds the chain (zoom blur if enabled, then `CrtEffect` if `oldTv`) and a `PostProcessing` with it; with no effect (or `POST_PROCESSING_ENABLED = false`) the arena goes on the stage. `renderArena()` sets `zoomBlur.center` to the core's screen position, then `post.render()`. `this.crt` becomes `this.post`.

### Phase 46 — Capture burst
- A second animation plays together with the atom's pull-in when the player captures an atom (see "Capture burst" in `docs/graphical-specs.md`): a ring grows from the center behind everything, in the captured atom's color, and fades out. Purely visual: no score, SFX or capture-rule change. Its numbers are constants at the top of `CaptureCircle.js`, which are the source of truth; the values here are the current ones, as examples.
- New `src/game/entities/CaptureCircle.js`: one instance per capture, so several captures close in time overlap and none interrupts another (unlike `AtomPulse` and `PaddleFlash`, which are one per atom / paddle and restart). It has its own `Graphics` view at the playfield's origin and a timer. The constructor takes the color, a snapshot of the atom's `color` at the moment of capture (later color changes don't matter).
  - Opacity is animated on `view.alpha` (a color fade was considered and dropped: it isn't cheaper in PixiJS, it would have to follow the background color, and overlapping circles would cover each other instead of blending).
  - The geometry is drawn only when the radius changes, never scaled (scaling would thicken the stroke), like `AtomEmitter.draw()`: `clear().circle(0, 0, radius).stroke({ width: CORE_RADIUS, color })`, so the stroke keeps the core's radius as its width at every size. It is drawn once at radius 0 in the constructor and stays untouched through the fade-in; it is redrawn each frame only during the growth. At most about three circles are alive at once, so this costs next to nothing.
  - Phase 1, 0 to `FADE_IN_TIME` (0.1 s): radius 0 (no redraw), alpha rises linearly from 0 to `PEAK_ALPHA` (0.5).
  - Phase 2, `FADE_IN_TIME` to `DURATION` (0.5 s, the same as the atom's pull-in, so it ends as the atom reaches the core): with `p` the progress through this phase, radius is `MAX_RADIUS_FACTOR` (1.25) × `RING_RADIUS` × `easeOutQuad(p)`, and alpha falls linearly from `PEAK_ALPHA` to 0.
  - `update(dt)` returns `false` once `DURATION` has passed. Imports `CORE_RADIUS` and `RING_RADIUS` from the entity files, like `PaddleFlash` does, taking care with circular imports (read the constants only inside methods if needed).
- `src/game/GameEngine.js`:
  - `buildScene()`: a `captureCircleLayer` container added first to `playfield`, so the circles are behind every gameplay element (the ring, paddles and their echoes, core, pulses and atoms): `captureCircleLayer, ring.view, flashLayer, paddleLayer, emitter.view, pulseLayer, atomLayer`. The ring and the core are outlines with no fill, so the burst shows through them.
  - A `captureCircles` array, empty at construction.
  - `captureAtCore()`: right after `target.startCapture()`, create a `CaptureCircle` with `target.color`, add its view to the layer and the circle to the array.
  - `update()`: tick every circle next to the paddle flashes, before the state `switch`, so they run in every state (a capture just before the timer ends still finishes during the core collapse). A finished circle leaves the array and its view is destroyed (`view.destroy()`), so nothing piles up in the scene. Pause freezes them, since everything runs on `app.ticker`. No state goes to React (rule 1).
  - Try Again and unmount need nothing extra: Try Again builds a new engine, and `arena.destroy({ children: true })` takes any leftover circle with it.
- Notes: a 25 px stroke on a radius-0 circle is a disc of about half that radius, and the outer edge at the end is about `1.25 × RING_RADIUS` plus half the stroke. Both are accepted. The post-processing (zoom blur, bloom, CRT) applies as with everything in the arena.
- Docs (as part of the implementation): `docs/graphical-specs.md` ("Capture burst" under "Visual feedback"; the "Capture" bullet points to it), `docs/project-structure.md` (`CaptureCircle.js`), `docs/implementation-status.md` (Phase 46).

### Phase 54 — Gamepad indicator on the Main Menu

**Why.** The menus and the game can be played with a controller, but nothing tells the player so. The Main Menu now shows whether a controller is detected (MAIN MENU and MAIN MENU - gamepad not detected mockups).

**The component: `src/components/GamepadIndicator.jsx`** (React, menus' HTML layer)

- It shows one line of text with a controller drawing below it. Only `standard`-mapping controllers count (the same rule as menu navigation), so a controller the game can't use is never "detected".

Both share the outline and the L1/R1 bumpers, so these are written once and only the inner details change (sticks, d-pad and face buttons, or the `?`).

It's a non-interactive informative text, like the How To Play instructions and the credits. It's one line, horizontally centered over the drawing; it's wider than the drawing and overflows it equally on both sides. Its bottom is about 27px above the drawing's top (about 548 → 575 in the mockup; to be confirmed against the mockup when it's built).

Mobile browsers are detected by a touch-only primary input, `matchMedia('(hover: none) and (pointer: coarse)')`. This is read once, when the component mounts. ### Phase 55 — Blinking buttons: ENTER BOUNCERBACK and pending levels

**Why.** Players unlock tiers by beating every level of the current one, but Level Select doesn't show which levels of a tier are already beaten. The name of an unlocked level that still needs beating now blinks. Decided with the user, after rejecting lowercase names (it breaks the uppercase rule), a filled / empty dot next to the name (no room beside the longest names, such as CHRONOSAEDR0N) and an underline on beaten levels (cluttered once most levels are beaten). Blinking marks the pending levels, which are always few: few levels are unlocked early on, and few are left late in the game. It's also an early arcade cue (the blinking 1UP).

The Intro's `ENTER BOUNCERBACK` button blinks too. It's the player's first click, so it teaches the cue from the start: a blinking button is the one to press next. Level Select then uses the same cue without explaining it.

**The blink** (the same everywhere)

- Only the button's text blinks: visible for 1 s, invisible for 1 s, with no fade (a hard on/off). It starts visible.
- The button's border, its size, the game controller's double border and the pressed look stay as they are, so nothing moves.
- Every blinking text on a screen is in sync, also when one starts blinking while the screen is shown (on Level Select, after the Konami Code's reset, see `docs/info-for-testers.md`).
- It keeps blinking while the button is selected with the game controller, and while a controller button or the mouse is held on it (the pressed look: inverted colors, with the text blinking in the inverted color).
- **On activation it stops:** when the button is activated (click, tap, or the controller's release, see Phase 35), its text becomes steadily visible and stays so through the screen-out, so the choice is readable as it fades out. Nothing is saved. Other blinking buttons keep blinking during the screen-out.

**Where it's used**

- **Intro:** `ENTER BOUNCERBACK` blinks from the screen-in on. The note above it ("Grab your best headphones first ;)") stays steady. The controller can't select this button (unchanged), so only the mouse and touch apply.
- **Level Select**, where a level button has three states:
  - Locked: `------------`, steady (unchanged).
  - Unlocked and not beaten (pending): the name blinks.
  - Beaten: the name is steady.
  - A pending level activated and then lost blinks again the next time Level Select is shown.
- No other button blinks.

**Implementation** (React / CSS only: menus' HTML layer; no PixiJS, no per-frame state)

- `src/components/Button.jsx`: a new `blinking` prop. The children always go in a `<span className="button__label">`, so the DOM never changes; `blinking` only adds `button__label--blinking` to it.
- `src/index.css`:
  - One shared clock per menu, so every blinking text stays in sync: a registered custom property `--blink` (`@property`, `<number>`, inherited, initial value 1), animated on `.menu__items` with `@keyframes blink` (1 for the first half, 0 for the second), 2 s, `step-end`, infinite.
  - `.button__label--blinking { opacity: var(--blink); }`. A button that starts blinking later reads the same clock, so it's in phase at once. Using `opacity`, not `visibility` or `display`, keeps the box and the layout fixed, and screen readers always read the text.
  - The clock is on `.menu__items`, not on `.screen` or its direct children: those get the screen transitions' `animation` (screen-out, shake, tint, screen-in), which would replace it. The texts still fade, tint and shake with their buttons as before. Both the Intro button and the level buttons are inside a `Menu`'s `.menu__items`; BACK is in `.menu__footer` and never blinks.
  - No new constants file: the 1 s / 1 s timing is in the CSS keyframes, like the screen transitions.
- `src/screens/IntroScreen.jsx`: `useState` for "activated", set in the button's `onClick` before `onEnter()`; the button gets `blinking={!activated}`.
- `src/screens/LevelSelectionMenuScreen.jsx`:
  - A level is pending when it's unlocked and its number isn't in `levelProgress.beatenLevels` (already passed in from `App.jsx`; `src/game/levelProgress.js` doesn't change).
  - `useState` for the activated level's number, set in the button's `onClick` before `onSelectLevel(level)`. The button gets `blinking={pending && level.number !== activatedLevel}`.
- Both are single, low-frequency changes (rule 2). A second activation can't happen: taps and controller presses are ignored during the screen-out.

**Docs** (as part of the implementation)

- `docs/graphical-specs.md`: a new "Blinking buttons" section (the blink, its timing, sync, the controller selection and pressed look, the steady text on activation, and where it's used), referenced from "Intro screen note" (the button blinks, the note doesn't) and from "Level Select" (the three states).
- `docs/game-rules.md`, "Level unlocking": one line saying Level Select shows the levels still to beat by blinking their name (see `graphical-specs.md`).
- `docs/design-decisions.md`, "Layout & UI": the decision and the rejected options (lowercase, dot, underline) with their reasons; why ENTER BOUNCERBACK blinks too; why How To Play doesn't mention it and why there's no reduced-motion fallback.
- `docs/info-for-testers.md`: the Konami Code reset makes every tier 0 level blink again.
- `docs/implementation-status.md`: Phase 55.
- `docs/game-instructions.md` is not changed (decided with the user): How To Play doesn't explain the blink, and players work it out from the Intro and from how Level Select changes as they progress. No reduced-motion fallback either: the game, the menu animation and the transitions don't follow that setting, and a 0.5 Hz text blink isn't the motion it protects from.

### Phase 56 — Paddle count per level

**Goal**

How many paddles can be set at the same time becomes a per-level value instead of a fixed two, so fast, dense levels can allow more (four, say). The level file's `paddles` object gets an optional integer `count` (see `docs/level-file-schema.json`, "Paddles" in `docs/game-rules.md` and "Paddle count" in `docs/design-decisions.md`). Setting one more paddle than the count removes the oldest (first in, first out), as today. If `count` is missing it is 2, so every existing level plays exactly as before.

Out of scope: changing any level's count (a level design choice, made afterwards by editing its file), and the How To Play text (`docs/game-instructions.md` says "Use the two paddles"; it is updated by hand, only if the user asks).

**Implementation**

- `docs/level-file-schema.json`: `paddles.count`, integer, optional, `"minimum": 1`, `"default": 2` (done with the docs). `npm run validate:levels` checks it with Ajv, `minimum` included.
- `src/game/levelLoader.js`:
  - `checkRanges`: `paddles.count`, when present, must be at least 1. The in-game schema check supports only a subset of JSON Schema, without `minimum`, so the game repeats the range here like the others.
  - `loadLevel`: a new runtime value `paddleCount: data.paddles.count ?? DEFAULT_PADDLE_COUNT`, with `DEFAULT_PADDLE_COUNT = 2` as a named constant next to the loader's other constants, and a comment that it matches the schema's default.
- `src/game/GameEngine.js`:
  - Remove `MAX_ACTIVE_PADDLES`; `setPaddle` and `updatePaddleWarnings` use `this.level.paddleCount`. Their comments say "the level's paddle count" instead of "a third one".
  - Nothing else changes: paddles come from the pool or are created on demand, so more paddles need no preallocation; the warning formula (`active + dragged − count`, oldest first) already handles any count, including two sticks dragging at once.
- No change in the level files.

**Docs** (with the plan)

- `docs/level-file-schema.json`: `paddles.count`.
- `docs/game-rules.md` ("Core mechanics", "Paddles"), `docs/game-controller.md` ("Gameplay"), `docs/graphical-specs.md` ("Paddle replacement warning") and `docs/design-decisions.md` ("Paddle count"): the paddle limit is the level's count, two by default.

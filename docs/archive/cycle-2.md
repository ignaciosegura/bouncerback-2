### Phase 8 — Pause functionality
- `src/screens/PauseOverlay.jsx` (the only overlay screen), per `navigation.md`, graphical-specs "Pause overlay" and the GAMEPLAY PAUSE MENU mockup: the Settings controls (MUSIC, SFX, OLD TV) inline, then EXIT TO MENU and `<<< RESUME`. There's no Settings button, so the Settings screen is never opened from Pause.
- OLD TV (on Settings and Pause) is the CRT switch from Phase 39, connected when the shader branch was merged. From the Pause overlay it changes the effects on the running engine (`GameEngine.setOldTv()`), so the level isn't restarted, and the frozen frame behind the overlay shows the change at once.
- Pausing stops `app.ticker` (as `P` does today); RESUME restarts it. EXIT TO MENU goes to the Main Menu with the usual screen transition; RESUME closes the overlay without one.
- The on-screen Pause button (top-right of the Game Screen in `navigation.md`) is out of scope for now: it will be decided later. Until then the touch-only mobile builds can only pause through auto-pause.
- Pause toggles (each opens the Pause overlay while playing, and resumes while it's open, like RESUME):
  - Keyboard: `P` (as today). Not Esc: once the game goes fullscreen, browsers use Esc to leave fullscreen and don't pass it to the page.
  - Game controller: the menu button (Xbox Menu, standard index 9; see `game-controller.md`). It works while playing and on the overlay; elsewhere it does nothing.
- When pausing is allowed: only while playing (`STATE.PLAYING`): the arena is fully drawn and the level music has started. Not during the 3-second start delay (`STARTING`), the core collapse (`COLLAPSING`) or the Game Over delay (`LOST`), and not after the end (`ENDED`). From the core collapse on, the level is over for the player: the music has ended and nothing can be done in-game anymore, so there's nothing to pause. Today `togglePause()` in `GameEngine.js` only blocks `ENDED`, so `P` pauses during the start delay too: fix it to pause only in `PLAYING` (resuming is always allowed). This applies to every pause trigger: `P`, the menu button and auto-pause.
- Auto-pause: the game pauses itself, with the overlay, when the tab is hidden (`visibilitychange` → `document.hidden`) or the window loses focus (`window` `blur`), so the level timer never runs while the player is away. Once the game goes fullscreen, leaving fullscreen (`fullscreenchange`) pauses too. It never resumes by itself: the player resumes with RESUME, `P` or the menu button. It follows the rule above, and does nothing when the game is already paused.
- Who owns what: the `GameEngine` owns the pause itself (ticker, music, SFX, input) and decides when it's allowed. It reports each change to React through a new low-frequency callback, `onPauseChange`. `GameScreen` keeps only `paused` (and the panel color) in React state and shows the overlay. The overlay's buttons call back into the engine. No frame-by-frame state reaches React.

### Phase 9 — Screen transitions
- Every screen change plays the same old-TV transition on the screen's elements: a 1 s **screen out**, then a 0.5 s **screen in** (see "Screen transitions" in Decisions and graphical-specs "Screen transitions"). All the visuals are CSS keyframes. JavaScript never animates anything: React only keeps the old screen up until its screen-out ends, then swaps.
- `src/index.css`:
  - `:root`: `--color-tint-yellow: #666600` and `--color-tint-red: #660000` (graphical-specs "Colors": transition dark yellow / dark red; the tint red isn't the one-life-left background color).
  - `@property --fg { syntax: '<color>'; inherits: true; initial-value: #FFFFFF; }` so `--fg` can be animated (a plain custom property would jump instead of blending). `.screen` and `.screen--light` keep setting it as today.
  - `.button:active, .button:focus-visible`, etc. already invert with `var(--fg)` / `var(--bg)`, so a pressed or focused button follows the tint too. No change.
  - New `/* Screen transitions */` block:
    - `.screen-transition`: `position: absolute; inset: 0;` (wraps the menu background and the screen; both are already `absolute; inset: 0`, so layout doesn't change). The wrapper itself never animates.
    - `.screen-transition--out::after, .screen-transition--in::after`: an invisible input shield on top of everything (`content: ''; position: absolute; inset: 0; z-index: 1;`), so every tap and click is ignored during a transition, the canvas included. (`pointer-events: none` on the wrapper wouldn't be enough: `.overlay button` sets `pointer-events: auto`, which overrides an inherited `none`.)
    - The elements: `.screen-transition--out .screen > :not(.game-screen__canvas)` gets `animation: screen-out 1s linear forwards, screen-shake 125ms linear 0.875s;`, and `.screen-transition--in .screen > :not(.game-screen__canvas)` gets `animation: screen-in 0.5s linear;`. The game canvas container is the only child of a screen that isn't an element (it acts as the Game Screen's background).
    - The tint: `.screen-transition--out .screen` gets `animation: screen-tint 0.5s linear 0.5s forwards;`. It changes `--fg` only; the screen's `background` (`var(--bg)`) doesn't move.
  - Keyframes:
    - `screen-out`: `opacity` 1 → 0.
    - `screen-tint`: `50% { --fg: var(--color-tint-yellow) } 100% { --fg: var(--color-tint-red) }`, with no `0%` keyframe, so it starts from the screen's own `--fg` (black or white) and needs no variant-specific keyframes. The 0.5 s delay holds that color for the first half of the screen-out.
    - `screen-shake`: `translateY` 0 → `calc(-2 * var(--u))` → `calc(2 * var(--u))` → 0 (25% / 75% / 100%), once, from 0.875 s to 1 s.
    - `screen-in`: `opacity` 0 → 1.

### Phase 13 — Level unlocking
- The levels are grouped in **tiers**, set by a new `tier` field in each level file. Only tier 0 is unlocked on a fresh install. When the player has beaten (reached You Win! on) every level of the highest unlocked tier, the next tier unlocks. Unlocked tiers stay unlocked across launches. *(The first version of this phase unlocked one level per win.)*
- Current tiers, decided with the user (the level files are the source of truth): level 1 is tier 0; levels 2, 3 and 4 are tier 1; level 5 is tier 2.
- **Scope:** the unlocking logic, its persistence, and the Level Select redesign: one row per tier (`LEVEL MENU.png`), with locked levels shown as dashes (`LEVEL MENU (LOCKED LEVELS).png`).

#### Level files
- `docs/level-file-schema.json`: new required property `tier`, `"type": "integer"`, no `default`. Description: the level's tier; tier 0 is unlocked from the start, and each further tier unlocks when every level of the tier before it has been beaten. Added to `required`. The `name` description adds "At most 14 characters (Level Select buttons are sized for that)"; the limit is checked by the loader, not with `maxLength`, which the loader's schema checker doesn't support.
- `src/levels/level1.json` … `level5.json`: add `"tier"` after `"name"` with the values above.
- `src/game/levelLoader.js`:
  - `checkRanges` adds `level.tier must be 0 or greater` (the schema check already rejects non-integers), and `level.name must be at most 14 characters`. The limit is an exported constant, `LEVEL_NAME_MAX_LENGTH = 14`, sized for the longest planned name (QUANTAMORPHICA, a level to be added later); Level Select sizes its buttons from it, so a longer name fails at load instead of overflowing its button.
  - `loadLevel` returns `tier: data.tier`.
  - After `levels` is built, a check across all level files, thrown like the mechanics-list check: the tiers must run from 0 with no gaps (every tier from 0 to the highest has at least one level). A gap would leave every tier after it locked forever.

#### Progress persistence
- New `src/game/levelProgress.js`, in the style of `highScore.js` and `oldTv.js` (every `localStorage` access in `try`/`catch`; storage unavailable means progress just won't persist).
- One key, `bouncerback.levelProgress`, holding JSON `{ "unlockedTier": n, "beatenLevels": [numbers] }`. Both are needed: `unlockedTier` is what the user asked to persist, and `beatenLevels` lets a tier be finished over several sessions (beat level 2, close the app, come back and beat 3 and 4). Levels are identified by their number (`levelN.json`), as everywhere else.
- `getLevelProgress()`: reads and sanitizes the stored value. Missing or malformed → `{ unlockedTier: 0, beatenLevels: [] }`; `unlockedTier` is clamped to 0 … highest tier; `beatenLevels` keeps only the numbers of existing levels.
- `registerLevelWin(levelNumber)`: adds the level to `beatenLevels` (no duplicates), then, while every level of `unlockedTier` is beaten and a higher tier exists, raises `unlockedTier` by one. Saves and returns the new progress. Beating a level again, or one from a lower tier, changes nothing else. The tier never goes down.
- `isLevelUnlocked(level, progress)`: `level.tier <= progress.unlockedTier`.
- The unlock rule is a pure function of `levels` and the progress (taking `levels` as an argument), so it's easy to reason about separately from storage.

#### Wiring (React only; no change to the GameEngine)
